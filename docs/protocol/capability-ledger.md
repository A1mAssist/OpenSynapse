## Latest Read-Only Capture

The GET-only runs are stored under `artifacts/protocol/2026-08-12/`; the physical-wake Viper confirmation is `artifacts/protocol/2026-08-13/source-backed-viper-physical-wake-fixed.json`. They used the `0001/0002`, 91-byte control collection and sent no SET command.

- Blade brightness returned status `0x02` with raw value `0xFF`.
- Blade thermal zones both returned status `0x02` and the same performance/fan state (`02/00`); fan target reads returned raw zone values `0x2D` and `0x14`.
- Blade charge limit returned status `0x02` with raw value `0xD0` (80%).
- Blade CPU/GPU boost GETs returned status `0x02` with cluster/value pairs `01/01` (CPU Medium) and `02/00` (GPU Low).
- Blade max-fan GET returned status `0x02` with raw value `00` (Disabled); its known remaining-packet mismatch is accepted only for command `078F`.
- Blade logo power/mode GETs returned status `0x02` with raw values `01` (On) and `00` (Static).
- Viper verified reads ended with timeout errors (`0x04`) in this run; the errors are preserved in both artifacts and do not change the existing `Verified` status earned by earlier write/readback/restore evidence. The result is consistent with the mouse being asleep: all Product 184 GETs fail together, while Blade Product 710 reads continue to succeed. Wake the mouse before the next probe; no write is needed.
- After physically waking the Viper on 2026-08-13, every baseline GET returned success (`0x02`). The corrected DPI-stage GET returned active stage 3/5 with `400,800,1600,3200,6400`; low-battery GET returned raw `0x4D`, or `30%` by the official dependency's integer conversion. Both remain `SourceBacked` and production writes stay disabled.

Viper battery chemistry is independently source-backed by the `00B8` Synapse USB captures attached to OpenRazer PR `#2149`: Alkaline, rechargeable NiMH, and Lithium were sent as `1F / size 01 / class 07 / command 14` with argument `00`, `01`, and `02`; the device returned success and echoed each report. The capture contains no chemistry GET, and the subsequent `0780` report only refreshes battery percentage. OpenSynapse therefore implements exact SET report builders and synthetic tests but exposes no sender, probe, telemetry, or UI control until an exact current-value read or another deterministic restoration path is established.

OpenRazer PR `#2149` routes PID `00B8` through transaction `1F` and the generic persistent DPI-stage request. That request is class/id `0486`, data size `26`, and argument `[01]` (`VARSTORE`), not `[00]`. Its documented response layout is `[storage, active, count]` followed by up to five seven-byte records `[stage, X_BE, Y_BE, 00, 00]`. Upstream's response comment shows one-based record IDs while its SET builder emits zero-based IDs, so the parser accepts only a complete contiguous sequence in either base and normalizes positions to `1..count`. The 2026-08-13 current-device response settled the actual `00B8` GET form as one-based with active stage 3; older `[00]` artifacts are superseded. No production write is enabled.

The Boost GET observations were followed by the write test below; the remaining `SourceBacked` observations do not promote those capabilities to `Verified`.

The same date's opt-in Boost hardware test first read both thermal zones and both Boost clusters, entered Custom mode while preserving fan mode, wrote the original CPU/GPU values unchanged, changed each cluster by one legal enum step, and read both clusters after each production setter. It restored the original CPU/GPU values and the pre-test performance mode in `finally`, with final GET verification. Production setters reject non-Custom mode, reject writes before a successful current-path read, verify the untouched sibling cluster, and attempt two-cluster restoration on failure or cancellation.

The 2026-08-12 Logo runs are retained as historical negative evidence. They sent only the then-current `0300`/`0302` reports, and the operator observed Static and Breathing remain physically off despite electronic readback; see `artifacts/protocol/2026-08-12/logo-static-left-target.json` and `logo-breathing-left-target.json`. That result led to the protocol correction and the controlled 2026-08-13 Static run below; it does not override the later successful evidence.

The 2026-08-13 controlled Static run used the corrected OpenRazer Blade report (`VARSTORE=01`, transaction `FF`) on `1532:02C6`, visually confirmed the physical logo lit during the ten-second hold, and restored the original Off state with successful electronic readback. See `artifacts/logo-validation-20260813-static-02.json`. This promotes only Off/Static; Breathing remains SourceBacked until separately visually validated.

The 2026-08-13 single-report Breathing check sent only `0302 [01,04,02]` for 60 seconds from the restored Off state and sent one final `0300 [01,04,00]` cleanup report. No physical light appeared. This is negative evidence for the standalone undocumented effect command, not evidence that the script needs extra guessed writes; the exact Synapse enable sequence is still required. See `artifacts/logo-validation-20260813-breathing-single-01.json`.

OpenRazer commit `4e65f1249587` records a hardware-tested fix for standard-matrix Starlight on a BlackWidow Chroma V2. Its working report keeps `data_size=0x01` while carrying the effect id, color mode, speed, and two RGB triplets through argument byte eight. OpenMaw independently preserves and documents that exact wire quirk because field devices accept it. OpenSynapse now builds the same bytes through a Starlight-only internal report path; it does not reinterpret the declaration as `0x09` or relax validation for ordinary reports. This resolves the construction ambiguity but does not promote `02C6` without its own visual/restore run.

The 2026-08-12 `030A` Static-red hardware attempt returned success acknowledgements for both the target and the explicit Static `#99DD72` restore command, but the operator observed neither the red target nor the green restoration on the keyboard. See `artifacts/protocol/2026-08-12/keyboard-static-red-visual.json`. This is negative visual evidence: a successful `030A` acknowledgement is not proof that the Blade's visible lighting engine applied the effect. No matrix test was run, and no capability was promoted.

The 2026-08-13 matrix takeover run used Software mode `0004 [03,00]`, the effect-8 lighting-engine gate `0F02 [00,00,08,00,00,00]`, and `030B` row batches. A cold-state A/B on 2026-08-15 resolved the missing commit: six rows followed by `030A [05,00]` on every frame rendered the corrected locator, while sending `030A [05,00]` only once before the row stream produced a solid color. Production therefore uses transaction IDs `1..7` per frame with 1 ms report delays despite the cached Product 710 manifest naming `rzDevice25LedMatrixSkipSetEffect`; physical device behavior is the controlling evidence. See `artifacts/protocol/2026-08-15/keyboard-matrix-custom-commit-01.json` and `keyboard-matrix-official-takeover-01.json`.
